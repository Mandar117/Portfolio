Problem Statement

Robot software needs two things to feel trustworthy: a control loop that runs exactly on time, every time, and a way to move data between programs as fast as possible. The default ROS2 toolkit does both reasonably well, but "reasonably well" isn't good enough when a robot arm is updating 1,000 times a second. This project builds a faster, more predictable communication layer for ROS2 from scratch, in C++, and backs every claim with real, measured numbers instead of assumptions.

Tools
C++20, ROS 2 Humble, CMake / colcon, Ubuntu 22.04 (WSL2), POSIX Shared Memory, GitHub Actions (CI), Python (pandas, matplotlib)

Completed
October 2026
  • Built a custom task scheduler ("executor") for ROS2 that wakes up a robot's control loop far more precisely than the standard one, cutting the typical delay from 154 microseconds down to 22 microseconds at 1,000 updates per second, measured across more than 530,000 samples.
  • Designed a direct shared-memory "shortcut" channel that lets two programs on the same robot exchange messages without going through the usual networking stack, about 3x faster when the system is idle, and still fast when the robot's CPU is under heavy load, where the standard approach slows down by roughly 50x.
  • Found and fixed a hidden bug inside ROS2 itself: its built-in timer was quietly running about 9% too fast, because it was reading time from two internal clocks that had silently drifted apart inside the test environment, a bug nobody would notice without specifically instrumenting for it.
  • Wrote 56 automated tests and set up continuous integration (CI), so every change to the code is automatically built, tested, and benchmarked before it counts as "done."
  • Reported every result together with the exact conditions it was measured under: what hardware, what operating-system limitations applied, instead of presenting numbers without context, because an untrustworthy benchmark is worse than no benchmark at all.

How It's Organized

Rather than one tangled program, the system is split into three layers that stack cleanly on top of each other. Each layer only needs to know about the layer directly beneath it, which means each piece can be built, tested, and trusted completely on its own, before anything is wired together.

The bottom layer has no idea it's being used for robotics at all: it's just two very fast, very predictable building blocks. The middle layer connects those building blocks to ROS2. The top layer is the actual experiment: a tool that runs every combination of scheduler and transport automatically, and records exactly what happened.

Layer 1 Foundation: the building blocksA super-fast queue and a super-fast memory manager, both built to never make the program wait and never ask the operating system for more memory mid-task. No knowledge of robots or ROS2 at all, reusable in any program.
Layer 2 Middleware: the custom scheduler + transportsThe custom executor that wakes the control loop on time, plus the three different ways of sending a message between programs (see the flowchart below).
Layer 3 Application: the experiment itselfA benchmarking tool that automatically runs every scheduler × transport × speed combination, and writes out the raw numbers, so every chart on this page comes from a real, repeatable run.

Three Ways to Send a Message

Whenever one program needs to tell another "here's the robot's new joint position," it has to choose how that message travels. This project builds and measures all three realistic options side by side, so the comparison is fair: same message, same rate, same machine.

Why this second chart matters most: the standard path is fine when the system is quiet, but under real load it gets roughly 50x slower at the worst case, exactly when a robot can least afford it. The shared-memory channel barely notices the load at all, because it doesn't share any of the same background threads the standard path depends on.

  • The clock bug: early results showed the standard ROS2 timer behaving impossibly: firing too often, with "negative" delay. Instead of assuming a bug in the new code, the investigation worked backwards into ROS2's own internals and found the real cause: the timer was scheduling itself against one internal system clock, but actually waiting against a second, slightly different one. On the test machine those two clocks had drifted about 9% apart, so a "1,000 times a second" timer was really firing about 1,091 times a second. Every benchmark run now automatically measures and reports this drift, so the condition can never quietly distort a result again.
  • Honesty about test conditions: all of these numbers come from testing inside a Windows-hosted Linux environment (WSL2), which does not allow the operating system's top-priority scheduling mode to be used. Real robot hardware would likely perform at least as well, probably better, but every number on this page is reported exactly as measured, with its test conditions stated plainly, rather than quietly assuming ideal conditions that weren't actually there.
